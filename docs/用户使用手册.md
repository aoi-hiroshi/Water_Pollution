# 水污染溯源与预测系统——用户使用手册

> 文档版本：V0.2（分类清洗与分析接入，Linux 联调待完成）  
> 适用项目：Qt 桌面端 + C++20 Muduo 服务端 + MySQL  
> 最后核对日期：2026-09-18

## 1. 系统简介

本系统用于展示水质样本、统计分析结果，并为后续污染源分类与水质趋势预测提供统一入口。

当前系统由三部分组成：

```text
Windows Qt 桌面端
        │ HTTP/JSON
        ▼
Linux Muduo API 服务
        │ 异步数据库任务
        ▼
      MySQL
```

一次数据查询的实际调用路径如下：

```text
Qt 页面
  → ApiClient / QNetworkAccessManager
  → Muduo HTTP Server
  → Router
  → Controller
  → WaterService
  → WaterRepository
  → DbExecutor
  → 动态线程池 + MySQL 连接池
  → MySQL
  → JSON 响应
  → Qt 表格、统计摘要和曲线
```

Qt 负责界面和结果展示；Muduo 负责网络通信；数据库线程池执行阻塞 SQL，避免数据库磁盘 I/O 卡住网络线程。

## 3. 使用前准备

### 3.1 推荐运行方式

- Windows：运行 Qt 桌面端。
- Linux 虚拟机：编译并运行 Muduo 服务端。
- MySQL：可以安装在 Linux 虚拟机本机，也可以使用可访问的独立数据库服务器。
- Windows 与 Linux 虚拟机必须网络互通，默认使用 TCP `8080` 端口。

仅进行界面查看时，可以直接启动 Qt 客户端；需要查看真实公司和水质数据时，必须先启动 MySQL 和 Muduo 服务。

### 3.2 软件要求

服务端建议准备：

- 支持 C++20 的 GCC；
- CMake 3.20 或更高版本；
- Muduo（`muduo_net`、`muduo_base`）；
- MySQL Client 开发库；
- Boost；
- nlohmann/json。
- ONNX Runtime C/C++（启用污染溯源或趋势预测时需要）。

Qt 客户端当前工程基于：

- Qt 5.12.8；
- MinGW 7.3 32-bit；
- Qt Widgets、Qt Network。

### 3.3 数据库最低结构要求

服务端当前会查询以下三张表：

- `company_info`：公司或污染源基础信息；
- `train_data`：训练样本；
- `test_data`：测试样本。

兼容当前代码的最小表结构示例：

```sql
CREATE DATABASE IF NOT EXISTS water_quality_system
  DEFAULT CHARACTER SET utf8mb4;

USE water_quality_system;

CREATE TABLE company_info (
    company_id   BIGINT PRIMARY KEY,
    company_name VARCHAR(128) NOT NULL,
    company_code VARCHAR(64) NOT NULL,
    task_type    VARCHAR(64) NULL,
    location     VARCHAR(255) NULL,
    description  TEXT NULL,
    created_at   DATETIME NULL
);

CREATE TABLE train_data (
    id                BIGINT PRIMARY KEY,
    temperature       DOUBLE NULL,
    ph                DOUBLE NULL,
    cod               DOUBLE NULL,
    nh3n              DOUBLE NULL,
    tp                DOUBLE NULL,
    water_level       DOUBLE NULL,
    orp               DOUBLE NULL,
    conductivity      DOUBLE NULL,
    dissolved_oxygen  DOUBLE NULL,
    turbidity         DOUBLE NULL,
    company_id        BIGINT NOT NULL,
    INDEX idx_train_company (company_id)
);

CREATE TABLE test_data LIKE train_data;
```

表中十个特征字段名必须与上例一致。分类模型是在异常检测和清洗后的数据上训练的，因此用于溯源的记录也应是清洗后的推理就绪数据；不要把未经处理的异常原始值直接交给模型。当前项目没有自动建表和 CSV 自动导入流程，需要预先导入样本数据。每个出现在 `company_info` 中的公司，只有在对应数据表存在样本时才能成功加载概览。

建议为程序创建独立数据库账号，不要在应用中使用 MySQL `root` 账号：

```sql
CREATE USER 'water_app'@'%' IDENTIFIED BY '请替换为强密码';
GRANT SELECT ON water_quality_system.* TO 'water_app'@'%';
FLUSH PRIVILEGES;
```

原表只需 SELECT；保存清洗版本还需给以下两张新表授予 INSERT，不需修改原始表的权限。

管理员在目标数据库执行 `server/sql/001_classification_cleaning.sql`，创建版本记录及清洗样本表。
新库可先运行 `server/sql/000_base_schema.sql`，再导入公司和样本数据。脚本不会替换已有表或自动迁移旧字段。

```sql
GRANT INSERT ON water_quality_system.classification_cleaning_runs TO 'water_app'@'%';
GRANT INSERT ON water_quality_system.classification_cleaned_samples TO 'water_app'@'%';
```

上例沿用已有账号；实际部署应限制账号来源地址。Qt 不直连 MySQL，不需要向 Windows 暴露 3306 端口。

## 4. 第一次启动

系统的正确启动顺序是：

```text
1. 启动 MySQL
2. 配置服务端环境变量
3. 启动 Muduo 服务端
4. 检查健康接口
5. 配置 Qt 的服务地址
6. 启动 Qt 客户端
```

### 4.1 在 Linux 中编译服务端

在项目根目录执行：

```bash
cmake -S server -B build/server \
  -DCMAKE_BUILD_TYPE=Debug \
  -DWATER_WITH_MYSQL=ON \
  -DWATER_WITH_MUDUO=ON \
  -DWATER_WITH_ONNX=ON \
  -DWATER_BUILD_TESTS=ON

cmake --build build/server -j
ctest --test-dir build/server --output-on-failure
```

如果 Muduo、MySQL 或 ONNX Runtime 安装在非系统目录，需要额外向 CMake 指定头文件和库路径。详细参数见 [Muduo 服务端说明](../server/docs/muduo_server.md)、[污染溯源推理说明](../server/docs/trace_inference.md)和[趋势预测推理说明](../server/docs/forecast_inference.md)。暂时只运行数据查询时，可以关闭 `WATER_WITH_ONNX`，此时两类推理接口会返回 503，数据查询仍可使用。

### 4.2 配置服务端

程序读取环境变量，不会自动加载 `.env` 文件。项目根目录的 `.env.example` 只是配置模板。

在启动服务的同一个终端中设置：

```bash
export WATER_SERVER_HOST=0.0.0.0
export WATER_SERVER_PORT=8080
export WATER_IO_THREADS=2

export WATER_DB_HOST=127.0.0.1
export WATER_DB_PORT=3306
export WATER_DB_USER=water_app
export WATER_DB_PASSWORD='请替换为数据库密码'
export WATER_DB_NAME=water_quality_system
export WATER_DB_POOL_MIN=2
export WATER_DB_POOL_MAX=8
export WATER_DB_QUEUE_CAPACITY=512

export WATER_TRACE_MODEL_PATH="$PWD/server/models/trace_random_forest.onnx"
export WATER_TRACE_MODEL_NAME=random_forest
export WATER_TRACE_MODEL_VERSION=1.0
export WATER_FORECAST_MODEL_PATH="$PWD/server/models/forecast_attention_lstm_h10.onnx"
export WATER_INFERENCE_CORE_THREADS=1
export WATER_INFERENCE_MAX_THREADS=2
export WATER_INFERENCE_QUEUE_CAPACITY=128
export WATER_ONNX_INTRA_OP_THREADS=1
```

配置项说明：

| 配置项 | 默认值 | 用途 |
| --- | --- | --- |
| `WATER_SERVER_HOST` | `0.0.0.0` | 服务监听地址；虚拟机对外提供服务时保持此值 |
| `WATER_SERVER_PORT` | `8080` | HTTP 服务端口 |
| `WATER_IO_THREADS` | `2` | Muduo 网络 I/O 线程数 |
| `WATER_DB_HOST` | `127.0.0.1` | MySQL 地址 |
| `WATER_DB_PORT` | `3306` | MySQL 端口 |
| `WATER_DB_USER` | 无 | 必填，数据库账号 |
| `WATER_DB_PASSWORD` | 无 | 数据库密码 |
| `WATER_DB_NAME` | 无 | 必填，数据库名 |
| `WATER_DB_POOL_MIN` | `2` | 最小数据库连接数，同时作为数据库核心工作线程数 |
| `WATER_DB_POOL_MAX` | `8` | 最大数据库连接数，同时作为数据库最大工作线程数 |
| `WATER_DB_QUEUE_CAPACITY` | `512` | 数据库任务队列容量 |
| `WATER_TRACE_MODEL_PATH` | 无 | Random Forest ONNX 模型路径；缺失时溯源接口不可用 |
| `WATER_FORECAST_MODEL_PATH` | 无 | Attention-LSTM ONNX 模型路径；缺失时预测接口不可用 |
| `WATER_INFERENCE_CORE_THREADS` | `1` | 推理线程池核心线程数 |
| `WATER_INFERENCE_MAX_THREADS` | `2` | 推理线程池最大线程数 |
| `WATER_INFERENCE_QUEUE_CAPACITY` | `128` | 推理任务队列容量 |
| `WATER_ONNX_INTRA_OP_THREADS` | `1` | 单次 ONNX 推理内部线程数 |

服务端会先创建数据库连接池，再启动 HTTP 监听。如果数据库账号、密码、地址或库名错误，服务不会进入监听状态。

### 4.3 启动服务端

只启用预测而尚未导出分类模型时，不要设置 `WATER_TRACE_MODEL_PATH`，这不会影响预测或数据查询。非空模型路径指向不存在/不兼容文件时，服务会在启动阶段报错退出。

```bash
./build/server/water_server
```

看到类似以下日志说明已经开始监听：

```text
water-api listening on 0.0.0.0:8080
```

需要停止服务时，在终端按 `Ctrl+C`。程序会停止事件循环，并等待已接受的数据库任务完成后关闭。

### 4.5 确认虚拟机地址

在 Linux 中查询虚拟机 IP：

```bash
ip addr
```

假设地址为 `192.168.1.100`，先在 Windows 浏览器中访问：

```text
http://192.168.1.100:8080/api/v1/health
```

若 Linux 本机可以访问、Windows 不能访问，应检查：

- 虚拟机网络是否为桥接模式或配置了 NAT 端口转发；
- Linux 防火墙是否允许 TCP 8080；
- 服务是否监听 `0.0.0.0`，而不是只监听 `127.0.0.1`。

### 4.6 配置并启动 Qt 客户端

必须在启动 Qt 程序之前配置后端地址。

后端与 Qt 在同一台计算机时：

```powershell
$env:WATER_API_BASE_URL = "http://127.0.0.1:8080"
```

后端在 Linux 虚拟机时：

```powershell
$env:WATER_API_BASE_URL = "http://192.168.1.100:8080"
```

环境变量设置完成后，需要从同一个 PowerShell 窗口启动程序；如果使用 Qt Creator，则可在项目的运行环境中添加 `WATER_API_BASE_URL`。

客户端工程文件位于：

```text
WaterLogin/WaterLogin.pro
```

最简单的构建方式是使用 Qt Creator 打开该文件，选择 Qt 5.12.8 MinGW 32-bit 套件，然后执行“构建”和“运行”。也可以在对应 Qt MinGW 环境中执行：

```powershell
qmake WaterLogin\WaterLogin.pro
mingw32-make
```

如果没有设置 `WATER_API_BASE_URL`，客户端默认连接 `http://127.0.0.1:8080`。设置页面当前只显示地址说明，尚不能修改或保存地址。

### 5.3 数据中心

这是已接入 Muduo API 的核心数据页面；实际使用前须先完成 Linux 服务端与真实 MySQL 部署联调。

进入主界面后，客户端会自动请求公司列表。正确加载时，“公司选择”下拉框会显示 `company_info` 表中的公司名称。

推荐操作顺序：

1. 左侧选择“数据”；
2. 将“任务模式”设为“溯源 / 分类数据预处理”；
3. 在“公司选择”中选择目标公司；
4. 在“数据源”中选择“训练数据 train_data”或“测试数据 test_data”；
5. 单击“刷新数据呈现”，或单击“查看统计信息与原始图”；
6. 查看上方样本数据预览；
7. 查看下方十特征曲线；
8. 在右侧查看公司编码、样本总数、均值、标准差、最小值和最大值。

概览按钮固定请求 10 条原始预览；新的分类清洗/分析使用全量统计，表格前 50 条、对比曲线最多 300 个抽样点。

页面展示的十项特征为：

| 中文名称 | 数据库字段 |
| --- | --- |
| 水温 | `temperature` |
| pH | `ph` |
| COD | `cod` |
| 氨氮 | `nh3n` |
| 总磷 | `tp` |
| 液位 | `water_level` |
| ORP | `orp` |
| 电导率 | `conductivity` |
| 溶解氧 | `dissolved_oxygen` |
| 浊度 | `turbidity` |

分类模式现在可以使用四个数据处理按钮：

1. “空值检测与修复”：按当前公司各特征中位数修复，整列为空不虚构数据。
2. “预览异常值清洗”：默认窗口 50、Z-score 阈值 3，异常点取前一个已修复值；不是完整卡尔曼滤波。
3. “确认并保存清洗新版本”：预览完成后可用；按预览参数重新读取、清洗并保存，不覆盖原表，返回版本编号。
4. “生成分布图”：选择特征及箱线/直方图；各公司对比使用原始数据、统一分箱。
5. “生成相关性图”：Pearson/Spearman 热力图；NA 表示常量或数据不足，不是零相关。
6. 保存后在“分析数据版本”中填版本号，分析清洗后数据；0 表示原始数据，概览按钮始终读取原始表。
7. “导出当前图 PNG”保存 Qt 绘制的结果。

曲线抽样可能隐藏部分异常，修复数量以全量摘要为准。保存时若原数据已变化，结果可能不同；请求超时不要反复保存，先检查版本表。
“预测数据预处理”模式仍为预留布局，不在本次分类接入范围内。
完整规则、请求示例、版本表和 Linux 部署步骤见 [分类数据处理指南](../server/docs/classification_preprocessing.md)。

### 5.4 污染溯源

该页面使用“分类任务”中的 Random Forest 模型完成污染源分类。训练阶段保存的 `StandardScaler` 和分类器会被合并进同一个 ONNX 文件，C++ 服务按固定顺序传入十项原始水质特征。

操作步骤：

1. 确认服务端已经使用 `WATER_WITH_ONNX=ON` 构建并成功加载模型；
2. 左侧选择“溯源”；
3. 选择测试数据 `test_data` 或训练数据 `train_data`；
4. 输入对应数据表中的样本 ID，填写数据页保存的“清洗版本”；0 仅用于已经准备好的原始表记录；
5. 单击“发起溯源”；
6. 查看最可能污染源、置信度、模型版本和六个公司的完整概率排名；
7. 单击“导出结果”，将候选排名保存为 UTF-8 CSV。

服务端不会使用样本记录中的 `company_id` 直接生成答案，而是读取十项水质特征后执行模型。模型标签 1～6 按 `company_info.company_id` 映射公司名称；数据库缺少某个公司映射时使用“公司N”作为回退名称。

### 5.5 趋势预测

该页面已经调用 `/api/v1/inference/forecast`。模型使用过去120条清洗后的水质记录，预测 COD、氨氮、总磷和浊度，最多10步。

使用前，按 [预测 ONNX 说明](../server/docs/forecast_inference.md)配置模型。项目已提供导出并验证的预测ONNX文件，重新训练后再运行导出脚本。给预测监测站准备独立的 `company_id`，按采样顺序导入预测文件夹的清洗后数据。不要直接使用随机排列的分类样本，也不要导入已标准化的 `*_scaled.csv`。

1. 进入“预测”，点击“刷新资源”，确认模型已加载；
2. 选择真实公司/监测站和训练或测试数据；
3. “截止ID”填 `0` 表示最新120条，或输入属于该公司的指定样本ID；
4. 选择未来1～10步，点击“开始预测”；
5. 切换指标，查看蓝色历史曲线和橙色未来预测曲线；
6. 查看四指标结果表格，点击“导出预测CSV”保存结果与模型版本。

当前数据库无真实采样时间字段，界面显示的是采样步数，不能解释成小时。未来真实值尚未到达，因此页面不会虚构 MAE、RMSE、R² 或置信区间。历史不足120条、特征缺失或模型不可用会明确提示。当前不自动保存预测结果到数据库。

### 5.6 日志中心

该页面预留了日志类型、级别和关键字筛选，以及结果导出操作。

当前日志表格是静态示例；“查询日志”和“导出”尚未接入数据库或服务端接口。

### 5.7 系统设置

该页面用于说明未来会管理的接口地址、数据库和模型资源。当前所有按钮为占位按钮，不能持久化配置。

现阶段应使用环境变量配置地址，不要依赖设置页面。

## 6. 已开放接口

所有接口使用 HTTP/JSON，成功响应统一为：

```json
{
  "code": 200,
  "message": "success",
  "data": {}
}
```

错误响应会额外带有稳定的 `error` 字段：

```json
{
  "code": 400,
  "error": "INVALID_ARGUMENT",
  "message": "错误说明",
  "data": null
}
```

| 方法 | 地址 | 功能 |
| --- | --- | --- |
| GET | `/api/v1/health` | 检查 Muduo 进程状态 |
| GET | `/api/v1/companies` | 获取公司列表 |
| GET | `/api/v1/data/overview` | 获取某公司的样本预览与统计摘要 |
| POST | `/api/v1/inference/classify` | 按数据库样本执行污染源分类 |
| GET | `/api/v1/inference/forecast/model` | 预测模型可用状态、历史长度与支持步数 |
| POST | `/api/v1/inference/forecast` | 同公司120条历史的四指标趋势预测 |
| POST | `/api/v1/data/classification/missing` | 空值修复预览/保存版本 |
| POST | `/api/v1/data/classification/clean` | 滑动 Z-score 异常修复预览/保存版本 |
| POST | `/api/v1/data/classification/distribution` | 特征分布与公司对比 |
| POST | `/api/v1/data/classification/correlation` | Pearson / Spearman 相关性 |

数据概览参数：

| 参数 | 是否必填 | 说明 |
| --- | --- | --- |
| `company_id` | 是 | 正整数，公司编号 |
| `dataset` | 否 | `train_data` 或 `test_data`，默认 `train_data` |
| `limit` | 否 | 1～50，默认 10 |

溯源请求体：

```json
{
  "sample_id": 1,
  "dataset": "test_data",
  "cleaning_run_id": 100
}
```

上述 100 是示例版本号，替换为真实清洗保存结果；省略或传 0 读取原始表。

预测请求体（公司7为示例，请替换成实际预测站点编号）：

```json
{
  "company_id": 7,
  "dataset": "test_data",
  "end_sample_id": 0,
  "horizon": 10
}
```

响应包含 `history`、`predictions`、历史起止ID、公司、数据集与模型版本。

## 7. 常见提示与处理方法

| 现象 | 可能原因 | 处理方法 |
| --- | --- | --- |
| 浏览器访问根地址显示 404 | 根路径没有注册页面 | 改为访问 `/api/v1/health` |
| Qt 提示“Connection refused”或无法连接 | 服务未启动、地址错误、端口未开放 | 先用 Windows 浏览器访问健康接口，再检查 `WATER_API_BASE_URL` |
| Qt 提示请求超时 | 15 秒内未收到响应 | 检查虚拟机网络、Muduo 日志和 MySQL 状态 |
| 服务启动后立即退出 | 数据库环境变量缺失或连接创建失败 | 检查用户、密码、库名、MySQL 地址和权限 |
| 公司列表为空 | `company_info` 没有数据 | 导入公司记录后重启客户端或重新进入主界面 |
| 数据概览显示未找到 | 公司无对应训练/测试样本 | 检查所选数据表中的 `company_id` |
| 返回 `DATABASE_ERROR` | 表名、字段名、字段类型或 SQL 执行异常 | 对照第 3.3 节检查数据库结构，并查看服务端日志 |
| 返回 `DATABASE_UNAVAILABLE` | 连接池在限定时间内没有可用连接 | 检查 MySQL 负载与连接数，必要时调整连接池上下限 |
| 返回 `SERVER_BUSY` | 数据库任务队列已满 | 降低并发请求或增大 `WATER_DB_QUEUE_CAPACITY`，同时分析慢 SQL |
| 设置页面修改无效 | 当前页面未实现保存 | 启动客户端前设置环境变量 |
| 溯源返回 `INFERENCE_UNAVAILABLE` | 未启用 ONNX、模型未导出或模型路径未配置 | 按推理说明导出模型，使用 `WATER_WITH_ONNX=ON` 重新构建并配置模型路径 |
| 溯源返回 `TRACE_SAMPLE_NOT_FOUND` | 所选数据表中不存在该样本 ID | 查询 `train_data`/`test_data` 的 `id` 后重新输入 |
| 溯源返回 `INVALID_TRACE_SAMPLE` | 十项特征存在 NULL 或非法数值 | 清洗或补齐该样本后重试 |
| 预测模型未加载/按钮不可用 | 模型路径未配置、未启用 ONNX 或公司列表为空 | 检查模型状态接口、`WATER_FORECAST_MODEL_PATH` 和预测数据，点击“刷新资源” |
| 预测返回 `INSUFFICIENT_HISTORY` | 所选公司/截止ID之前不足120条 | 补齐同公司历史或使用更晚的截止ID |
| 预测返回 `FORECAST_SAMPLE_NOT_FOUND` | 截止ID不存在或属于其他公司 | 按所选公司和数据集查询实际样本ID |
| 预测返回 `INVALID_FORECAST_HISTORY` | 特征NULL/非法值或窗口混入其他公司 | 对照预测特征协议检查清洗后记录 |

## 8. 面试演示建议流程

一次完整演示可控制在 5～8 分钟：

1. 用架构图说明 Qt、Muduo、业务层、数据库线程池和连接池的职责；
2. 在 Linux 中启动 `water_server`，展示启动日志；
3. 调用健康接口，证明网络层可用；
4. 调用公司列表接口，证明数据库链路可用；
5. 登录 Qt，进入数据中心切换公司和训练/测试数据；
6. 展示表格、十特征曲线和统计摘要；
7. 说明 MySQL 查询不会阻塞 Muduo I/O 线程，而是提交给有界动态线程池；
8. 输入测试样本 ID，展示数据库线程池切换到独立推理线程池后的六分类结果；
9. 展示120条历史的ONNX趋势预测、四指标曲线/表格和CSV导出；
10. 最后说明部署计划：CMake 构建、Docker 化、日志持久化和接口压测。

演示时要主动说明当前边界。把占位页面说成已经实现会削弱项目可信度；清楚解释“完成了什么、为什么这样分层、下一步怎样扩展”更接近真实开发交流。

## 9. 当前限制与下一阶段

当前版本尚未包含：

- 用户表、密码加密、会话与权限控制；
- CSV 上传/导入接口迁移（分类清洗已支持独立版本保存，不覆盖原始表）；
- 两类模型的 Linux Muduo/MySQL 端到端实机验证；
- 通用任务表、推理结果持久化和日志表（已有分类清洗版本与样本表）；
- Qt 内的可编辑设置；
- Docker 镜像、反向代理和生产监控；
- HTTPS、限流、认证和生产级安全配置。

建议下一阶段按以下顺序推进：

1. 在 Linux 虚拟机完成 Qt → Muduo → MySQL 的真实联调；
2. 增加数据库初始化脚本和演示数据；
3. 配置已提供的分类 ONNX，执行清洗版本 SQL 并完成 Linux 清洗→保存→分类实机验证；重新训练后再运行导出器；
4. 运行 `tools/export_forecast_model.py`，准备预测时序数据并验证 `/api/v1/inference/forecast`；
5. 增加任务状态和日志持久化；
6. 补接口测试、并发测试、Docker 与部署文档。
